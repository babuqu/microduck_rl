> 目标读者：没接触过 RL、没接触过 mjlab，但想读懂"这个机器人走路策略是怎么被训练出来的"。
> 读完这份文档，你应该能回答：机器人**看到什么**、**能做什么**、**怎么被打分**、**怎么一步步学会走路**。

## 0. 一句话总览

这个文件是一份**"训练说明书"**。它本身不包含任何算法代码，只回答一个问题：

> "让 MicroDuck 这只小双足机器人在仿真里学走路，应该怎么设定这门课？"

它用 960 行 Python 配置，告诉训练系统：机器人长什么样、装了哪些传感器、每一步看到什么、能输出什么动作、每一步怎么打分、什么时候算摔倒、每次开局要随机扰动哪些物理参数、训练难度怎么循序渐进，以及最后用哪个 PPO 网络结构去学。

**类比**：这不是菜谱正文，而是一张"给 AI 老师的教学大纲"。AI 老师（PPO 算法）照着这份大纲，把机器人练会。

---

## 1. 读之前先懂 6 个概念（大白话版）

| 术语 | 大白话 | 在本文件哪里体现 |
|---|---|---|
| **Observation（观测）** | 机器人每一步"看到什么"——关节角度、身体倾斜、角速度、指令等 | `cfg.observations` |
| **Action（动作）** | 机器人每一步"输出什么"——14 个舵机各自转到哪个目标角度 | `cfg.actions["joint_pos"]` |
| **Reward（奖励）** | 每一步的"加减分"。走得像给正分，摔倒/抖/滑给负分 | `cfg.rewards` |
| **Command（指令）** | 老师给机器人下的命令："现在向前走 0.3 m/s""头转向左" | `cfg.commands` |
| **Domain Randomization（域随机化，DR）** | 每次开局随机变一点物理参数（重量、摩擦、传感器误差），逼机器人学出"到真机上也能用"的本事，而不是只会在仿真里走 | `cfg.events` |
| **Curriculum（课程）** | 由易到难：先在平地上学走，再加扰动；先小幅摆头，再大幅摆头 | `cfg.curriculum` |

另外两个常出现的名词：
- **actor（演员）**：真正用来控制机器人的策略网络。它看到的观测就是真机上传感器能拿到的东西。
- **critic（评论家）**：训练时用来评估"当前局面好不好"的网络。它能看到真机上没有的"上帝视角"数据（比如机器人真实的线速度），帮 actor 学得更快，但部署到真机时不用它。

## 3. 顶部：全局开关和参数（1–97 行）

文件最上面是一堆大写常量。它们的作用只有一个：**把"要不要开某个训练技巧"变成一行能改的开关**，不用翻到下面几百行去翻代码。

### 3.1 任务本身的关键设定

```python
NUM_STEPS_PER_ENV = 24
TURN_IN_PLACE_FRACTION = 0.15   # 15% 的环境专门练原地转圈
```

- `NUM_STEPS_PER_ENV = 24`：PPO 每次"抽一次经验"，每个并行环境走 24 步。后面所有课程表的"第几步"都要用它换算：`iteration × 24` 才是真实环境步数。
- `TURN_IN_PLACE_FRACTION = 0.15`：作者踩过坑——如果完全随机给指令，"原地转圈"这种情况只占 2% 的训练数据，机器人就学不会原地转。所以**人为强制 15% 的环境专门练这个**。这是"补数据缺口"的典型做法。

### 3.2 域随机化开关（ENABLE_*）

```python
ENABLE_COM_RANDOMIZATION = True        # 随机身体重心位置
ENABLE_MASS_INERTIA_RANDOMIZATION = True  # 随机质量和转动惯量 ±5%
ENABLE_JOINT_FRICTION_RANDOMIZATION = True  # 随机关节摩擦
ENABLE_VELOCITY_PUSHES = True         # 走得好好的，隔几秒推一把
ENABLE_IMU_ORIENTATION_RANDOMIZATION = True  # IMU 装歪了
ENABLE_ENCODER_BIAS = True             # 编码器读数有固定误差
```

**为什么要随机这些？** 因为仿真里的机器人是"完美"的，真机上的机器人是"不完美"的：电池电压会变、关节摩擦会变、装 IMU 时可能偏了几度、编码器有零点误差。如果机器人只在完美世界里训练，到了真机上一碰到不完美就摔。所以训练时**故意每局都给它制造一点不完美**，逼它学会"不管怎样都能站稳"。

注意几个被关掉的开关（`= False`），旁边注释写着 `# Was True`：
```python
ENABLE_KP_RANDOMIZATION = False   # Was True
ENABLE_KD_RANDOMIZATION = False   # Was True
```
意思是作者试过随机化电机 PD 增益，但发现反而不好，就关了——这些都是**实验留下的开关**。

### 3.3 随机化范围参数

紧接着的 `COM_RANDOMIZATION_RANGE = 0.003`、`VELOCITY_PUSH_RANGE = (-0.3, 0.3)` 等，就是每个开关的"力度"。注释里能看到很多教训，例如：

```python
VELOCITY_PUSH_RANGE = (-0.3, 0.3)  # 原来是 ±0.5
```
注释解释：原来推得太狠（±0.5 m/s，比它最大走路速度 0.4 还大），导致机器人被训练成"随时紧张"的神经质步态，改成 ±0.3 之后步态更从容。

## 4. 地形和辅助函数（135–200 行）

```python
MICRODUCK_ROUGH_TERRAINS_CFG = TerrainGeneratorCfg(...)
```

这是"粗糙地形"模式下生成的地面长什么样。小机器人抬脚高度只有 1–2 cm，所以台阶最高只有 1.5 cm（默认是 10 cm）。里面配了四种地形按比例混合：平地 25%、台阶 25%、随机凹凸 30%、缓坡 20%。

`_soften_terrain_contacts()` 是一个修补函数：让地形的碰撞接触"软一点"，避免硬棱角产生数值爆炸（NaN）导致训练崩溃。这种细节是纯工程踩坑。

## 5. 核心函数 `make_microduck_velocity_env_cfg()`（203–919 行）

这是整个文件的主体。它**不是从零开始造环境**，而是调用 `make_velocity_env_cfg()`（mjlab 框架自带的一个通用行走模板），然后**在它基础上改**——换成 MicroDuck 的机器人模型、换掉奖励、加上 MicroDuck 特有的随机化和指令。

> 这是读这个文件最重要的视角：**它是"改配置"，不是"写算法"**。你看到的 `cfg.rewards["xxx"].weight = ...` 这种语句，就是在调整默认模板里某项的权重。

### 5.1 传感器（229–265 行）

配了三个传感器：

| 传感器 | 作用 |
|---|---|
| `feet_ground_contact` | 探测左脚、右脚是否踩在地上、受力多大 |
| `self_collision` | 探测机器人自己的腿有没有撞到身体 |
| `foot_height_scan` | 用激光/射线看脚底离地面多高（判断脚抬起来没） |

### 5.2 Action 动作（280–283 行）

```python
joint_pos_action.scale = 1.0
```

意思是：机器人每个时间步输出的 14 个数，**直接对应 14 个舵机的目标关节角**（不做缩放）。这是最直观的控制方式——神经网络直接告诉每个关节"你转到这个角度"。

### 5.3 Reward 奖励（285–369 行，重点！）

这是整个文件最核心的部分。Reward 就是"考试评分标准"，机器人会想尽一切办法把总分最大化。理解每个 reward 在奖励什么，就理解了机器人最终会走出什么步态。

**主任务奖励（让它听话地走）：**

| 奖励项 | 权重 | 大白话 |
|---|---|---|
| `track_linear_velocity` | +2.0 | 实际前进速度和指令速度差多少，越准分越高 |
| `track_angular_velocity` | +2.0 | 实际转身速度和指令角速度差多少 |
| `head_pose_tracking` | +2.0 | 头的姿态跟上头部指令（这是这个任务的一大重点） |
| `air_time` | +3.0 | 脚离地时间在 0.125–0.3 秒之间给分——鼓励正常的步态迈步，而不是拖地 |

**姿态/平衡奖励（让它站得直）：**

| 奖励项 | 权重 | 大白话 |
|---|---|---|
| `pose` | +1.0 | 腿关节保持在接近 HOME 姿态（走路时放宽，站立时收紧） |
| `upright` | +2.0 | 躯干保持竖直，前倾/后倾都扣分。注释里写了为什么是 2.0 而不是 1.0：原来 1.0 时身体前倾 4° 几乎不扣分，机器人就一直弓着背走 |

**惩罚项（让它别做傻事）：**

| 奖励项 | 权重 | 大白话 |
|---|---|---|
| `foot_slip` | −0.1 | 脚在地上打滑扣分。特意只给 −0.1（而不是 −1.0），因为这个机器人转向靠枢轴转，惩罚太重就转不了弯 |
| `action_rate_l2` | −0.1（课程会加重到 −1.0） | 相邻两步动作变化太大扣分——防止电机抖动。训练初期轻，等步态稳了再加重 |
| `body_ang_vel` | −0.05 | 身体角速度太大扣分（别乱晃） |
| `angular_momentum` | −0.02 | 角动量太大扣分 |
| `self_collisions` | −1.0 | 自己撞到自己扣分 |
| `foot_clearance` | 目标 2 cm | 走路时脚要抬到 2 cm 高，否则拖地板 |

> **读 reward 的诀窍**：正权重 = 鼓励，负权重 = 惩罚。但要注意符号约定——文件里有些函数本身返回的就是"惩罚值（≤0）"，这种函数配**正**权重。作者在 AGENTS.md 里反复强调：**每一次训练都要去 wandb 检查每个 penalty 项是不是 ≤0，如果是正数说明符号写反了，机器人会在"奖励自己摔"。**

### 5.4 Events / 域随机化（371–539 行）

"事件"分几种触发时机：

- `startup`：整个训练开始时执行一次（比如展开 BAM 摩擦字段）。
- `reset`：每一局结束、机器人重置时执行——**大部分 DR 都在这里**，每局重新随机一次。
- `interval`：每隔几秒执行一次——比如"推一把"。

具体随机化了什么：
- 身体重心左右偏移 ±3 mm（课程会加到 ±15 mm）
- 头部各零件的重心
- 整机质量和转动惯量 ±5%
- 关节摩擦 ±10%
- 电机转子惯量 ±10%
- 每 3–6 秒沿 x/y 方向推一把（±0.3 m/s 的速度扰动）
- IMU 装歪最多 6°
- 每个关节编码器有 ±0.015 rad 的固定偏差

**终止条件**（392–396 行）：
```python
cfg.terminations["nan_state"] = ...
```
物理仿真出现 NaN（数值爆炸）就立刻重置这一局，否则坏数据会污染神经网络权重。

### 5.5 Observation 观测（541–645 行）

这是机器人"每一步看到什么"的清单。关键操作：

1. **删掉 actor 不该看到的东西**（542–547 行）：
   - 删掉 `base_lin_vel`（真实线速度）——真机上没有这个传感器，不能让 actor 依赖它。
   - 删掉 `height_scan`（地形激光扫描）——这个机器人身上没装。
2. **把 `base_lin_vel` 只给 critic**（550–553 行）：评论家可以看真实线速度，但演员不能。这就是"特权信息"。
3. **给观测加噪声和延迟**（597–600、618–623 行）：
   - 关节位置噪声 ±0.001、关节速度噪声 ±0.25、角速度噪声 ±0.03……
   - 关节速度故意延迟 1 个控制周期——因为真实 Dynamixel 固件算出的速度本来就有延迟。
4. **编码器偏差只给 actor**（640–643 行）：actor 看到带偏差的关节角（像真机器人的编码器读数），critic 看到真值。

> **为什么要这样设计？** 这就是 sim2real 的核心：**训练时让 actor 看到的东西，和真机上传感器实际输出的东西尽可能像**（有噪声、有延迟、有偏差），但 critic 训练时可以开上帝视角。

### 5.6 Commands 指令（647–711 行）

老师给机器人下的命令，分三组：

```python
# 1. 速度指令：前进/横移/转身
command.ranges.lin_vel_x = (-0.4, 0.4)   # 前后
command.ranges.lin_vel_y = (-0.3, 0.3)   # 左右横移
command.ranges.ang_vel_z = (-1.0, 1.0)   # 转身

# 2. 头部姿态指令（4 维：低头/抬头/摇头/歪头）
cfg.commands["head_pose"] = ...

# 3. 身体姿态指令（6 维：位置 xyz + 姿态 rpy）
cfg.commands["body_pose"] = ...   # 这个任务里权重设为 0，只是保留通道
```

最终观测拼起来是固定的 61 维：
```
[本体感觉 48 维] + [twist 速度 3 维] + [head_pose 4 维] + [body_pose 6 维]
```
**为什么必须固定 61 维？** 因为真机运行时会热切换不同策略（走路、站立、翻跟头），所有策略都必须用同样长度的输入，才能随时换上去。

### 5.7 姿态跟踪奖励（713–755 行）

新增了三个 reward：
- `head_pose_tracking`（+2.0）：头要跟住头部指令——这是这个任务区别于普通走路任务的重点。
- `body_pose_tracking`（权重 0）：身体姿态跟踪功能在，但**关掉**（保留观测通道给别的任务用）。
- `head_pose_bias`（权重 0，课程会升到 3.0）：专门惩罚"头一直往下耷拉"这种静态偏差。注释里讲了一段血泪史：作者试过把头跟踪的容差收紧，结果机器人干脆不走路了（因为它那个 280g 的头走路时本来就会晃，紧约束让"站着不动"成了最优解），最后改成只惩罚"恒定下垂"，不惩罚动态晃动。

### 5.8 Curriculum 课程（786–917 行）

这是"由易到难"的排课表。每个课程都是一个阶梯：到了第几步训练，就把某个参数调到下一档。

举几个例子：

**动作平滑度**（788–801 行）：
```
iter 0:   action_rate 惩罚 -0.1   ← 刚学走路，别抖得太狠就行
iter 500:  -0.2
iter 1000: -0.6
iter 1500: -1.0                  ← 步态稳了，再要求动作干净
```
为什么不一上来就 -1.0？因为初学走路时，严格的动作平滑惩罚会让机器人觉得"最好别乱动"，它就站着不动了。**先让它学会走，再要求走得好看。**

**站立环境比例**（804–817 行）：
```
iter 0:   2% 的环境要求它站着不动
iter 2000: 25% 的环境要求它站着不动
```
先让它学会走，再逐步要求它会"停下来站稳"。

**头部指令范围**（826–839 行）：
```
iter 0:   头只允许小幅度动 ±0.05 rad
iter 2000: 可以动到机械极限 ±1.1 rad
```
先小范围学，再放开。

**重心随机化范围**（861–879 行）：
```
iter 0:   重心随机 ±3 mm
iter 1500: ±15 mm
```
注释里写了教训：原来加到 ±30 mm 超过了脚的支撑多边形，机器人怎么都学不会向后走。

## 6. PPO 超参数（922–959 行）

最后一段 `MicroduckRlCfg` 是算法本身的配置，不涉及"教什么"，只涉及"怎么学"：

```python
actor.hidden_dims = (512, 256, 128)   # 策略网络：三层全连接，512→256→128
critic.hidden_dims = (512, 256, 128)  # 评论网络一样大
obs_normalization = True              # 观测归一化（导出 ONNX 时必须烤进去）
clip_param = 0.2                      # PPO 的裁剪参数
learning_rate = 1e-3                  # 学习率（自适应调度）
gamma = 0.99                          # 未来奖励折扣
lam = 0.95                            # GAE 参数
max_iterations = 50_000               # 最多训 5 万轮（实际几千轮就够）
```

这些是 PPO 算法的标准旋钮，新手不用一开始就调，知道"神经网络长这样、优化器这么配"就够了。

## 8. 新手读这个文件最该记住的 5 件事

1. **这是"改"出来的配置，不是从零写的。** 大部分默认值来自 `make_velocity_env_cfg()`，本文件只覆盖 MicroDuck 需要的部分。
2. **Reward 设计 = 机器人最终行为。** 它会最大化总分。你惩罚什么不够，它就钻什么空子（打滑、暴力摆头、站着不动）。
3. **actor 看到的 = 真机传感器输出**（有噪声、延迟、偏差）；critic 开上帝视角。这条线千万别搞混。
4. **课程的核心原则是"先会走，再走好"**——任何严格的平滑/精度约束都必须在技能学会之后再加重，否则机器人选择"什么都不做"。
5. **注释比代码值钱。** 这个文件里几乎每一行关键改动旁边都写着"原来是多少、为什么改、哪次实验翻车了"——那些是真正的工程知识。
